# 分支与发布规范

## 目标

- `main` 始终指向最新一次正式发布，并保持与最新版本 tag 一致。
- 每个大版本同时最多保留 3 个常驻分支：`main`、`dev/v<major>`、`release/v<major>`。
- 功能、修复、文档分支都是短期 PR 分支，合并后立即删除，不计入常驻分支。
- tag 是版本事实来源；不为每个小版本长期保留一条开发分支。

## 分支职责

| 分支 | 职责 | 生命周期 |
| --- | --- | --- |
| `main` | 已验收、已发布的稳定代码 | 永久 |
| `dev/v2` | 当前大版本下一版本的集成分支 | 永久，跟随大版本演进 |
| `release/v2` | 发布冻结、候选验收和紧急修复 | 发布窗口内创建，完成 tag 后删除 |

当前 v2 阶段：

- `main` 等于最新正式 tag。
- `dev/v2` 承接 v2.5.2 及后续 v2.x 开发。
- 需要发布时再从 `dev/v2` 创建 `release/v2`，验收完成后合入 `main` 并打 tag。

## 推送流程

### 常规版本

1. 从 `dev/v2` 创建短期分支，例如 `feat/v2.5.2-panel-material` 或 `fix/v2.5.2-login-readability`。
2. 向 `dev/v2` 提 PR；Ubuntu、Windows、前端和后端检查必须全绿。
3. 合并后删除短期分支。
4. 发布冻结时从 `dev/v2` 创建 `release/v2`。
5. 候选版本验收通过后，将 `release/v2` 合入 `main`。
6. 在 `main` 打 `vMAJOR.MINOR.PATCH` tag，并发布 Release。
7. 将 `main` 回合并到 `dev/v2`，删除 `release/v2`。

### 紧急修复

1. 从 `main` 创建 `fix/v2.x.y-*`。
2. 向 `release/v2` 提 PR，验收后合入 `main` 并打 patch tag。
3. 将 `main` 回合并到 `dev/v2`。

## 保护规则

- `main` 禁止直接 push、force push 和删除。
- `main` 只接受 `release/v2` 或紧急修复 PR。
- `release/v2` 在发布冻结期间禁止直接 push。
- 合并前必须通过 Ubuntu、Windows、前端和后端检查。
- tag 创建后不可移动；需要修复时发布新的 patch tag。
- 每次发布后校验 `main` 与最新 tag 指向同一提交。
- UI 相关 PR 必须附桌面、移动和主题截图；不得提交内网地址、凭据、构建产物或个人数据。

## 命名约定

- 常驻分支：`main`、`dev/v2`、`release/v2`。
- 短期分支：`feat/v2.5.2-<topic>`、`fix/v2.5.2-<topic>`、`docs/v2.5.2-<topic>`。
- 版本 tag：`v2.5.2`；预发布 tag：`v2.5.2-beta.1`。
- 合并提交使用 `feat:`、`fix:`、`docs:`、`build:`、`release:` 前缀。
