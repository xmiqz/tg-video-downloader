# 分支与发布规范

## 目标

- `main` 是唯一正式主线，始终等于最新正式 Tag，并且始终可发布。
- 不再长期维护 `develop`、`dev/v2` 或任何平行开发主线。
- Tag 是版本事实来源；所有发布资产对应同一个 Git SHA。
- 一个正式主线、一个版本号、一个发布 SHA、一套发布流程。

## 分支结构

| 分支 | 职责 | 生命周期 |
| --- | --- | --- |
| `main` | 已验收、已发布的稳定代码 | 永久，唯一长期分支 |
| `feat/<topic>` | 新功能 | PR 合并后删除 |
| `fix/<topic>` | 普通修复 | PR 合并后删除 |
| `hotfix/<topic>` | 正式版紧急修复 | PR 合并后删除 |
| `docs/<topic>` | 文档与截图 | PR 合并后删除 |
| `release/<version>` | 确实需要冻结期时使用 | 发布完成后删除 |

## 推送流程

1. 从最新 `main` 创建短期分支。
2. 完成后推送分支并向 `main` 提 PR，默认 Squash Merge。
3. CI 必须全绿：Ubuntu、Windows、前端、后端；涉及 Docker 时还要通过 amd64/arm64 验证。
4. 合并后删除短期分支。
5. 在通过验证的 `main` 提交上创建 `vMAJOR.MINOR.PATCH` Tag。
6. Tag 触发桌面端与 Docker 构建；Docker 先验证后发布。
7. 发布后校验资产 SHA-256、镜像 Tag、多架构 manifest 与 Release 状态。

紧急修复：从 `main` 创建 `hotfix/<topic>`，走同样 PR 流程，发布 patch Tag。

## 保护规则

- `main` 禁止直接 push、force push 和删除。
- 合并前必须通过 CI；不允许为了赶进度跳过检查。
- Tag 创建后不可移动；需要修复时发布新的 patch Tag。
- 每次发布后校验 `main` 与最新 Tag 指向同一提交。
- UI 相关 PR 必须附桌面、移动和主题截图；不得提交内网地址、凭据、构建产物或个人数据。
- 正式 Tag 构建不得额外生成 `dev-<SHA>` 镜像标签。

## 命名约定

- 长期分支：仅 `main`。
- 短期分支：`feat/<topic>`、`fix/<topic>`、`hotfix/<topic>`、`docs/<topic>`。
- 版本 Tag：`v2.5.2`；预发布 Tag：`v2.5.2-beta.1`。
- 提交前缀：`feat:`、`fix:`、`docs:`、`build:`、`chore:`、`release:`。
